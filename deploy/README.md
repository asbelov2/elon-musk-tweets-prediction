# Размещение TweetScope на Timeweb Cloud

Подготовлен вариант для **отдельного облачного сервера**: Docker Compose, публичный сайт, Caddy с автоматическим HTTPS и постоянный том SQLite. Все функции открыты всем: расчёты, сбор, импорт и добавление рынков. Каталог и история общие для посетителей; настройки бюджета остаются в браузере. Это одна инсталляция с одной базой, без личных кабинетов.

Для начала подойдёт Ubuntu 24.04 LTS, **2 vCPU, 2 ГБ RAM и 20 ГБ SSD**. Запускайте **один экземпляр приложения**: SQLite хранится локально, а предпросмотры импорта — в памяти процесса. Модель выполняет не более двух прогнозов одновременно. При росте посещаемости сначала увеличьте ресурсы сервера. Статический хостинг без Node.js и постоянного диска для этого проекта не подходит.

## 1. Сервер и домен

1. Создайте сервер в Timeweb Cloud и подключитесь по SSH.
2. Установите Git и [Docker Engine с Compose v2](https://docs.docker.com/engine/install/ubuntu/), если их ещё нет. Должны работать `docker version` и `docker compose version`.
3. Направьте A-запись домена или поддомена, например `tweets.example.com`, на IPv4 сервера. AAAA-запись должна вести на этот же сервер по IPv6 либо отсутствовать.
4. В сетевом экране Timeweb разрешите входящие TCP 80 и 443, а также ваш SSH-порт. UDP 443 необязателен и нужен для HTTP/3. Порт приложения 18080 остаётся доступен только на самом сервере.

Для отдельного сервера не нужно устанавливать Nginx: HTTP/HTTPS обслуживает контейнер Caddy. Если на машине уже есть Nginx или другой прокси, используйте альтернативу в конце инструкции.

## 2. Код и настройки

```bash
git clone https://github.com/asbelov2/elon-musk-tweets-prediction.git tweetscope
cd tweetscope
cp .env.example .env
chmod 600 .env
```

Если репозиторий закрытый, настройте на сервере SSH deploy key с доступом на чтение и клонируйте по SSH. Не помещайте GitHub-токен в URL команды или в Dockerfile.

В `.env` задайте собственный домен **без `https://` и пути**:

```dotenv
APP_DOMAIN=tweets.example.com
WRITE_ACCESS=public
```

`compose.https.yaml` автоматически передаст приложению `PUBLIC_URL=https://tweets.example.com`. Этим устраняется проблема Origin при работе за HTTPS-прокси. Остальные значения можно оставить из примера. XTracker не требует токена X.

Если используете официальный API X, задайте `X_BEARER_TOKEN` в `.env` на сервере. При `WRITE_ACCESS=public` все посетители могут запускать запросы с общим ключом и расходовать его лимит. Оставьте ключ пустым, если хотите использовать только бесплатные публичные данные XTracker. Файл `.env`, история и резервные копии исключены из Git и Docker-контекста.

## 3. Запуск с HTTPS

После обновления DNS:

```bash
docker compose -f compose.yaml -f compose.https.yaml up -d --build
docker compose -f compose.yaml -f compose.https.yaml ps
docker compose -f compose.yaml -f compose.https.yaml logs --tail=100
```

Откройте `https://tweets.example.com`, заменив имя своим. Caddy получает и продлевает сертификат автоматически. Для выпуска сертификата домен уже должен указывать на сервер, а 80/443 должны быть доступны извне. Сам сертификат и внешний DNS можно проверить только после размещения на вашем сервере.

Первый запуск создаёт пустую базу. Через интерфейс выберите аккаунт, соберите историю XTracker, проверьте предпросмотр и подтвердите сохранение. Затем загрузите нужный рынок и выполните прогноз. Текущие периоды можно добавить через форму; даты старых встроенных примеров не обновляются автоматически.

Тома `tweetscope_tweetscope_data`, `tweetscope_caddy_data` и `tweetscope_caddy_config` сохраняют историю, каталог и TLS-данные при пересоздании контейнеров. **`docker compose down -v` удаляет эти данные**; для обычных обновлений эту команду не используйте.

## 4. Перенос существующей базы

Если нужна история из локальной установки, сначала соберите проект (`npm ci && npm run build`) и сделайте согласованную резервную копию:

```bash
npm run backup -- /absolute/path/tweetscope-transfer.sqlite3
```

Команда использует путь `TWEET_DB` из окружения или `.env`, по умолчанию `data/tweets.sqlite3`. Она копирует всю SQLite-базу, включая каталог, снимки и подтверждённые WAL-записи. Произвольное копирование одного `tweets.sqlite3` при работающем сервере может пропустить WAL.

Передайте полученный файл по SSH на новый сервер. Для **пустой новой инсталляции** после первого создания тома:

```bash
docker compose stop app
docker compose run --rm -T --no-deps --entrypoint sh app -c 'cat > /app/data/tweets.sqlite3' < ./tweetscope-transfer.sqlite3
docker compose -f compose.yaml -f compose.https.yaml up -d
```

Проверьте каталог и количество часов в интерфейсе. Существующую рабочую базу перед заменой сохраните отдельной резервной копией. Восстановление из резервной копии выполняйте после остановки приложения; файлы старой базы и её WAL/SHM сначала сохраните отдельно, чтобы не смешивать их с восстановленной копией.

## 5. Резервные копии и обновления

Согласованная копия работающей базы:

```bash
docker compose exec -T app node dist/scripts/backup.js
```

Файл появится в `/app/data/backups/` с датой UTC в имени. Команда не перезаписывает существующие файлы. Переносите копии с сервера в отдельное хранилище: каталог `backups` находится на том же диске и сам по себе не защищает от потери сервера. Получить файл на сервер-хост можно командой `docker compose cp app:/app/data/backups/ИМЯ_ФАЙЛА ./ИМЯ_ФАЙЛА`.

Обновление с сохранением данных:

```bash
docker compose exec -T app node dist/scripts/backup.js
git pull --ff-only
docker compose -f compose.yaml -f compose.https.yaml up -d --build
```

Просмотр состояния и журналов:

```bash
docker compose ps
docker compose logs --tail=100 app
docker compose -f compose.yaml -f compose.https.yaml logs --tail=100 caddy
```

Контейнер проверяет `/api/health`; endpoint не обращается к внешним API. Приложение принимает SIGTERM и корректно закрывает SQLite. Время завершения ограничено, чтобы обновление не зависало на внешнем источнике.

## Настройки

| Переменная                          | Назначение                                                                                                                                                           |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APP_DOMAIN`                        | Домен для HTTPS-конфигурации Compose, без схемы и пути.                                                                                                              |
| `TWEETSCOPE_HTTP_PORT`              | Локальный порт хоста; по умолчанию `18080`.                                                                                                                          |
| `PUBLIC_URL`                        | Точный внешний origin для HTTP или своего прокси. HTTPS-конфигурация Compose формирует его из `APP_DOMAIN`.                                                          |
| `TWEET_DB`                          | Путь SQLite; в контейнере `/app/data/tweets.sqlite3`. На этот каталог нужен постоянный том.                                                                          |
| `WRITE_ACCESS`                      | `public` по умолчанию: все функции всем. `admin` — необязательный режим ограничения изменений.                                                                       |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Только для `WRITE_ACCESS=admin`: имя по умолчанию `admin`, пароль минимум 16 символов. Вход по ссылке «Администратор». Просмотр, демо и расчёты остаются публичными. |
| `TRUST_PROXY_HOPS`                  | Число доверенных прокси, в Compose `1`. Приложение слушает только за прокси; Nginx/Caddy должны заменять входящий X-Forwarded-For.                                   |
| `HTTP_RATE_LIMIT`                   | Общий лимит запросов на IP за минуту, по умолчанию `120` в production. Прогноз — до 6 запросов в минуту на IP. Health check не блокируется.                          |
| `X_BEARER_TOKEN`                    | Необязателен, нужен только для официального API X.                                                                                                                   |

Для `HTTP_RATE_LIMIT` и других дополнительных параметров используйте `environment` в Compose override; произвольные переменные из `.env` не передаются контейнеру автоматически. Ограничение частоты защищает доступность общего сервера и не закрывает функции за авторизацией.

В публичном режиме все посетители могут менять общую историю и каталог. Если позже понадобится отдельный доступ к управлению, задайте `WRITE_ACCESS=admin`, `ADMIN_PASSWORD` и пересоздайте контейнер. Пароль не нужен для публичного режима и не запрашивается у обычных посетителей.

## Если используется существующий Nginx

Запустите только приложение:

```bash
docker compose up -d --build
```

Задайте в `.env` `PUBLIC_URL=https://tweets.example.com`. Добавьте **отдельный** server block из [nginx.conf.example](nginx.conf.example), заменив домен и, если нужно, порт. Проверьте `sudo nginx -t`, затем выполните `sudo systemctl reload nginx`. Для HTTPS подключите сертификат привычным способом, например Certbot. Конфигурации первого проекта не заменяйте. `compose.https.yaml` в этом варианте не запускайте, чтобы не занимать порты Nginx.

## Проверки сборки

```bash
npm ci
npm run check
npm run test:e2e
docker build -t tweetscope:local .
npm run test:docker
```

Docker-проверка запускает реальный образ, выполняет прогноз в worker, импорт и онлайн-бэкап, пересоздаёт контейнер с тем же томом и проверяет сохранность данных и штатное завершение. Используется отдельный одноразовый том, который затем удаляется; рабочая база не затрагивается. GitHub Actions выполняет эти проверки без ключей X и без размещения сайта.

Если сборка идёт в корпоративной/облачной среде с собственным доверенным CA, его можно передать только на время сборки через BuildKit: `docker build --secret id=build_ca,src=/path/to/trusted-ca.pem -t tweetscope:local .`. CA не сохраняется в итоговом образе; TLS и integrity-проверки npm остаются включены. На обычном сервере Timeweb этот параметр не требуется.
